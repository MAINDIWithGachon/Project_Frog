# 뒤끝 백엔드 작업지침

## 목적

현재 Unity 프로젝트의 `RuntimeData.cs`는 인게임 유저 데이터의 Single Source of Truth 역할을 한다.

뒤끝 연동 작업의 목표는 `RuntimeData`가 가진 데이터를 뒤끝 DB에 안정적으로 저장하고, 로그인 후 다시 복원하는 것이다.

중요한 방향은 다음과 같다.

- `RuntimeData`는 인게임 데이터 보유, 수정, JSON 직렬화/역직렬화 담당
- `RuntimeDataBackendRepository`는 뒤끝 DB와 통신하는 중간 다리 담당
- UI, 성장, 재화, 스킬, 장비 등 게임 로직은 뒤끝 SDK를 직접 호출하지 않음
- 최초 버전은 재화, 스킬 레벨, 스탯 레벨, 성장 데이터부터 안정적으로 연결

## 현재 RuntimeData 저장 구조

현재 저장 대상 JSON 구조는 아래 형식을 기준으로 한다.

```json
{
  "Currency": {
    "Gold": 10000,
    "UpgradeStone": 100,
    "Gem": 10000
  },
  "skillLevels": [
    { "skillId": 0, "level": 1 },
    { "skillId": 1, "level": 3 },
    { "skillId": 2, "level": 5 }
  ],
  "statLevels": {
    "attackLevel": 10,
    "hpLevel": 8,
    "hpRegenLevel": 3,
    "critChanceLevel": 6,
    "critDamageLevel": 4
  },
  "growth": {
    "growthLevel": 1,
    "nowExp": 0,
    "growthPoint": 0,
    "attackLevel": 1,
    "hpLevel": 1,
    "critDamageLevel": 1
  }
}
```

이 구조는 그대로 유지한다.

저장 시에는 `RuntimeData.ExportJson(false)` 결과를 뒤끝 DB의 `dataJson` 컬럼에 문자열로 저장한다.

로드 시에는 뒤끝 DB에서 `dataJson`을 가져와 `RuntimeData`에 다시 주입한다.

## 권장 클래스 구조

새 파일로 `RuntimeDataBackendRepository.cs`를 만든다.

역할은 다음과 같다.

```text
뒤끝 DB
  <-> RuntimeDataBackendRepository
      <-> RuntimeData
          <-> 인게임 UI / 성장 / 재화 / 스킬 / 장비 로직
```

`RuntimeDataBackendRepository`가 담당할 작업:

- 뒤끝 `Backend.GameData.GetMyData` 호출
- 뒤끝 `Backend.GameData.Insert` 호출
- 뒤끝 `Backend.GameData.UpdateV2` 호출
- row 존재 여부 판단
- row `inDate` 관리
- `dataJson` 저장/로드
- 저장 실패/로드 실패 처리
- 저장 데이터 크기 체크

`RuntimeData`가 담당할 작업:

- 현재 세션의 유저 데이터 보유
- 재화, 스킬, 스탯, 성장 데이터 수정
- 현재 데이터를 JSON으로 내보내기
- 서버에서 받은 JSON을 다시 `RootData`로 복원
- 누락 필드 기본값 보정

## RuntimeData에 필요한 메서드

현재 `RuntimeData`에는 `ExportJson(bool pretty = true)`가 있다.

뒤끝에서 받은 JSON을 적용하려면 반대 방향 메서드가 필요하다.

예상 형태:

```csharp
public void ImportJson(string json)
{
    root = JsonUtility.FromJson<RootData>(json);
    EnsureValid();
    RaiseDataChanged();
}
```

구현 시 주의:

- 빈 문자열, null, JSON 파싱 실패를 방어한다.
- 파싱 실패 시 기본 데이터로 진행할지, 로그인/게임 진입을 막을지 정책을 정한다.
- `EnsureValid()`를 반드시 호출해 기존 유저의 누락 필드를 보정한다.
- 적용 후 `OnDataChanged` 이벤트를 발생시켜 UI가 갱신되게 한다.

## 뒤끝 테이블 설계

권장 테이블명:

```text
PlayerRuntimeData
```

또는

```text
USER_RUNTIME_DATA
```

유저당 row 1개를 기준으로 한다.

권장 컬럼:

```text
schemaVersion       int
dataJson            string
lastSavedAt         string 또는 DateTime
clientBuildVersion  string, 선택
```

초기 버전에서는 `dataJson` 하나에 `RuntimeData` JSON을 통째로 저장한다.

장점:

- 현재 `RuntimeData` 구조와 잘 맞음
- 구현이 단순함
- 재화 차감과 스킬 레벨업 같은 연관 변경을 한 번에 저장 가능
- 저장 구조가 조금 늘어나도 뒤끝 테이블 스키마 변경이 적음

단점:

- 일부 필드만 바뀌어도 전체 JSON을 다시 저장해야 함
- 운영툴에서 특정 필드 검색/집계가 어려움
- 데이터가 커지면 400KB 제한을 의식해야 함(크게 신경안써도 될듯)

## Insert와 Update 사용 원칙

`Insert`는 최초 생성용으로만 사용한다.

매 저장마다 `Insert`를 호출하면 같은 유저의 row가 계속 쌓이므로 금지한다.

권장 흐름:

```text
1. 로그인 성공
2. GetMyData로 PlayerRuntimeData row 조회
3. row 없음
   - RuntimeData의 기본 JSON을 dataJson으로 Insert
   - Insert 성공 시 반환된 inDate 저장
4. row 있음
   - row의 dataJson을 RuntimeData에 Import
   - row의 inDate 저장
5. 이후 저장
   - 저장해둔 inDate 기반으로 UpdateV2 호출
```

저장 시에는 `Backend.GameData.UpdateV2(tableName, inDate, Backend.UserInDate, param)` 계열을 우선 사용한다.

조건 기반 `Update`는 조건이 없으면 가장 최근 row를 수정하는 식으로 동작할 수 있어 장기적으로 헷갈릴 수 있다.

## 로드 흐름

로그인 성공 후 호출한다.

현재 `GuestLoginController`에는 로그인 성공 후 유저 정보 로드가 끝나는 지점에 데이터 로드 TODO가 있다.

권장 흐름:

```text
GuestLogin 성공
-> SHBackndUserInfo.LoadData 성공
-> RuntimeDataBackendRepository.Load(runtimeData)
-> RuntimeData 준비 완료
-> 게임 오브젝트/UI 초기화
```

로드 상세:

```text
1. 뒤끝 초기화 여부 확인
2. 로그인 여부 확인
3. GetMyData로 현재 유저의 PlayerRuntimeData 조회
4. row가 없으면 신규 유저로 판단
5. 신규 유저면 RuntimeData.ExportJson(false)를 Insert
6. 기존 유저면 dataJson을 RuntimeData.ImportJson으로 적용
7. schemaVersion이 낮으면 마이그레이션 또는 기본값 보정
8. 로드 완료 결과 반환
```

## 저장 흐름

저장은 명시적인 `Save(RuntimeData runtimeData)` 메서드로 제공한다.

저장 상세:

```text
1. RuntimeData.ExportJson(false) 호출
2. UTF-8 byte 크기 체크
3. Param 생성
   - schemaVersion
   - dataJson
   - lastSavedAt
   - clientBuildVersion, 선택
4. inDate가 없으면 Insert
5. inDate가 있으면 UpdateV2
6. 결과 bool 또는 enum 반환
```

초기 저장 타이밍:

- 로그인 후 신규 데이터 생성 시
- 게임 종료 시
- 앱 백그라운드 진입 시
- 중요한 성장/재화 변경 후

추후 개선:

- dirty flag
- 일정 시간 debounce
- 저장 실패 시 재시도 큐
- 서버 응답 대기 중 중복 저장 방지

## 400KB 제한 관련

뒤끝 요청 데이터는 400KB 제한을 의식해야 한다.

현재 재화, 스킬 레벨, 스탯 레벨, 성장 데이터는 매우 작으므로 당장 문제될 가능성은 낮다.

문제가 될 수 있는 영역:

- 장비 수백 개 이상
- 인벤토리 아이템 대량 저장
- 긴 문자열이 포함된 커스텀 데이터
- 필드 이름이 긴 장비 옵션 데이터

저장 전 크기 체크를 넣는다.

예상 코드:

```csharp
int byteSize = System.Text.Encoding.UTF8.GetByteCount(json);
Debug.Log($"RuntimeData save size: {byteSize / 1024f:F1} KB");

if (byteSize > 350 * 1024)
{
    Debug.LogWarning("RuntimeData save payload is close to BACKND 400KB limit.");
}
```

400KB에 가까워지면 장비/인벤토리 분리를 검토한다.

## 하나로 저장할 데이터와 분리할 데이터

초기에는 아래 데이터를 하나의 `dataJson`으로 저장한다.

```text
PlayerRuntimeData
- Currency
- skillLevels
- statLevels
- growth
```

장비/인벤토리가 본격적으로 커지면 분리한다.

권장 확장 구조:

```text
PlayerCoreData
- Currency
- growth
- statLevels

PlayerSkillData
- skillLevels

PlayerEquipmentData
- ownedEquipments
- equippedSlots
```

다만 지금 단계에서 너무 일찍 쪼개면 로드/저장 실패 처리와 정합성 관리가 복잡해진다.

현재는 하나의 JSON으로 시작하고, 장비/인벤토리 데이터가 커질 때 장비부터 분리하는 방향을 권장한다.

## 콘텐츠 추가와 버전 관리

서비스 중 콘텐츠가 추가되어 저장 내용이 늘어날 수 있다.

이를 위해 `schemaVersion`을 반드시 저장한다.

예:

```json
{
  "schemaVersion": 1,
  "dataJson": "{ ... }"
}
```

저장 구조가 바뀌면 `schemaVersion`을 올린다.

로드 시 권장 흐름:

```text
1. schemaVersion 읽기
2. dataJson 파싱
3. 낮은 버전이면 마이그레이션 적용
4. EnsureValid로 누락 필드 기본값 보정
5. 필요하면 최신 schemaVersion으로 다시 저장
```

단순 필드 추가:

```text
Energy 추가
stageProgress 추가
quest 추가
```

기존 유저 JSON에 필드가 없어도 기본값을 넣으면 된다.

배열/목록 추가:

```text
ownedEquipments 추가
achievementStates 추가
```

없으면 빈 배열 또는 기본 상태로 시작한다.

기존 필드 이름/의미 변경:

```text
Gold -> SoftCurrency
growth.attackLevel -> growthStats.attackLevel
```

이 경우에는 단순 기본값 보정으로 부족하다. 명시적인 마이그레이션이 필요하다.

콘텐츠 마스터 데이터:

- 스킬 정의
- 장비 템플릿
- 스테이지 정의
- 강화 비용표

이런 데이터는 유저 저장 데이터에 전부 넣지 않는다.

유저 데이터에는 유저가 가진 상태만 저장한다.

예:

```text
새 스킬 추가
-> 모든 유저 JSON에 즉시 추가할 필요 없음
-> 유저가 안 배운 스킬은 저장 데이터에 없음
-> GetSkillLevel에서 못 찾으면 0으로 취급
```

## 예외 처리 정책

로드 실패:

- 네트워크 오류
- 뒤끝 초기화 실패
- 로그인 미완료
- dataJson 파싱 실패
- 테이블/컬럼 누락

정책을 명확히 정해야 한다.

권장:

- 서버 로드 실패 시 게임 진입을 막고 재시도 버튼 제공
- 개발/에디터 테스트 모드에서는 mock/default 데이터 사용 가능
- 파싱 실패 시 에러 로그와 함께 기본 데이터로 진행할지 여부를 별도 정책으로 분리

저장 실패:

- `bool`만 반환해도 되지만, 가능하면 실패 사유를 알 수 있는 enum 또는 결과 객체를 반환한다.
- 저장 실패 시 UI에 즉시 노출할지, 조용히 재시도할지 정책을 정한다.
- 중요한 재화 소모 후 저장 실패가 발생하면 중복 지급/중복 차감 방지 정책이 필요하다.

## 요약

`RuntimeData`는 그대로 인게임 데이터 원본으로 두고, 뒤끝 연동은 `RuntimeDataBackendRepository`로 분리한다.

초기 버전은 `PlayerRuntimeData` 테이블에 `schemaVersion`, `dataJson`, `lastSavedAt`을 저장한다.

최초 생성은 `Insert`, 이후 저장은 `inDate` 기반 `UpdateV2`를 사용한다.

로그인 후 `Load`, 저장 시 `RuntimeData.ExportJson(false)` 기반 `Save`, 서버에서 받은 JSON은 `RuntimeData.ImportJson`으로 적용하는 흐름으로 구현한다.

장비/인벤토리는 처음부터 무리하게 분리하지 않고, 데이터가 커지거나 400KB 제한에 가까워질 때 별도 테이블로 분리한다.
